## Tres defectos cazados ANTES de correr, no después

1. **El binding admin habría dado 404 siempre:** `getRouteKeyName()` es `token` (para la ruta
   pública), así que las rutas admin con `whereNumber` resolvían por token → nada matcheaba.
   Rutas admin con campo explícito `{devolucion:id}` + ids explícitos en los llamadores.
2. **El correo del reembolso inline se habría duplicado:** el handler corre en AMBOS caminos
   (auto-aprobado inline y diferido), así que avisar también desde `resolver()` mandaba dos
   correos al cliente en el camino inline. El aviso vive SOLO en el handler.
3. **El aviso al cliente en el camino diferido es atómico:** en prod la cola es `database`
   (misma BD) — las filas del aviso commitean/rollbackean con la transacción de aprobación.

## Llamadas a criterio que el plan no fijaba (declaradas)

- **`devolucion.recibida` y `devolucion.resuelta` van AL CLIENTE** (mail externo); solo
  `solicitada` es interna (jefe_bodega + jefe_ventas + admin). Es el «notificar» con que la
  biblia cierra A-12. El plan decía «recibida (al solicitante interno)», que era ambiguo — el
  solicitante de una devolución ES el cliente.
- **`manage devoluciones` → jefe_bodega y jefe_ventas** (bodega recibe; ventas evalúa con el
  cliente, como describe A-12). Ajustable desde Roles sin tocar código.
- **El formulario público v1 lleva UN producto por envío** (descripcion + cantidad, texto
  libre — el cliente no conoce SKUs); la tabla soporta N ítems y bodega puede refinar. Para
  varios productos, el cliente registra más de una devolución (mismo trade-off que el ingreso
  por unidad del QR v1).
- **Sin badge del menú en este lote** (sería «devoluciones por recibir», cabe en la doctrina
  de badges) — anotado como pulido para no inflar el lote.
